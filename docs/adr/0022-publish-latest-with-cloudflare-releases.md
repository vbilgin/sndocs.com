# ADR-0022: Publish latest with immutable Cloudflare releases

- **Status:** Accepted
- **Supersession note:** [ADR-0023](0023-publish-from-a-local-operator-workstation.md) supersedes this decision's execution environment and approval gate only; the release model, immutability, retention, and Worker behavior below remain in effect.
- **Date:** 2026-07-28
- **Decision owner:** Victor Bilgin
- **Related commit:** `3411dec` (`Implement latest-release Cloudflare deployment`)
- **Supersedes:** [ADR-0002](0002-versioned-families-and-archive-retention.md) for scheduled publication selection, [ADR-0005](0005-host-agnostic-release-artifacts.md), and [ADR-0017](0017-remediate-ui-findings-at-source.md) only where it requires every current family in a release build

## Context

A complete current-family site is several gigabytes and repeatedly building every upstream family is too expensive for the initial hosting budget. Users still need stable family URLs, and any family once published as latest must remain available after a later family supersedes it. Cloudflare R2, Workers, CDN caching, and the zone security layer can provide a private durable origin and public serving path without Pages or an additional origin service.

The public build CLI already supports selecting one complete family and must retain its default complete-current-family behavior for local validation and a future publication-policy expansion. Deployment state must not require downloading archived family trees, and production rollback must select immutable state rather than mutate a live origin.

## Decision

Scheduled publication uses a latest-with-archives policy. It builds only the family currently identified as latest. A previously published latest family remains at its stable `/<family>/` URL as an immutable archive. Upstream families that were never published are not introduced merely because discovery still lists them. A same-family SHA or pipeline-fingerprint change replaces that family's active mapping with a new immutable artifact; a new latest archives the former latest. Local `sndocs build` retains its existing default behavior.

Store private R2 family trees below `content/{family}/{artifact_id}/`, with the artifact ID derived from family, exact source SHA, and pipeline fingerprint. Store release roots below `releases/{release_id}/root/` and a versioned small release manifest at `releases/{release_id}.json`. Derive the release ID from the canonical release manifest. Object-level family inventories verify paths, counts, bytes, and digests before candidate publication. Update only the mutable preview pointer after all candidate objects verify. Production has no mutable pointer: its Worker version captures the approved release ID.

Serve both preview and production with the same Worker code and private R2 binding. Preview resolves its pointer and sets a no-index policy. Production deployment sends the approved version to 100% traffic; rollback restores the preceding Worker version. The Worker implements clean directory URLs, `GET`, `HEAD`, conditional and byte-range requests, family-specific 404s, content metadata, release-separated cache keys, diagnostic release headers, and baseline security headers with CSP initially report-only.

Retain all family artifacts referenced by the active public release, every public archived family indefinitely, the preceding production release, and unreferenced artifacts for a 14-day grace period. Cleanup first emits a digestible deletion plan and never selects a referenced or sole archived-family artifact.

Keep the rolling GitHub Release as an independent host-agnostic recovery channel. Publish the changed family archive, root archive, checksums, release manifest, and reconstruction metadata. Split archives above 1.9 GiB deterministically. Do not remove the existing monolithic recovery artifact until reconstruction from the new assets has been proven.

## Consequences

- Routine publication builds, indexes, uploads, and validates only one complete family.
- Public history grows only when a family has actually been latest, while stable family URLs and archived content remain intact.
- R2 becomes durable deployment state; GitHub Releases remain an independent disaster-recovery channel rather than incremental build input.
- Production rollbacks are Worker-version changes and do not copy or mutate multi-gigabyte trees.
- Pipeline changes rebuild only current latest; already archived bytes remain immutable even when generated by older pipeline behavior.
- Release planning and root assembly use small metadata objects instead of downloading archived content.
- The Free Workers plan and standard GitHub runners remain cost boundaries; exceeding either requires an explicit decision.
- First deployment requires a preview bootstrap and manual DNS, certificate, security, rollback, and observation rollout.

## Alternatives considered

- **Continue publishing every current upstream family:** Deferred because initial build time, runner disk, upload volume, and storage growth are disproportionate to the cost target.
- **Publish latest and delete all prior families:** Rejected because it breaks stable historical URLs and the archive-retention promise.
- **Use Cloudflare Pages for the generated tree:** Rejected because multi-gigabyte release trees and immutable family retention fit private object storage plus a Worker origin more directly.
- **Use a mutable production pointer:** Rejected because a pointer change is less auditable and rollback-safe than a versioned Worker binding.
- **Rebuild archived families after pipeline changes:** Rejected because it spends resources, changes historical output, and risks losing the only reproducible public copy after upstream branch deletion.
- **Use R2 Infrequent Access or Cache Reserve initially:** Rejected pending measured access patterns and a separate cost decision.
